# Реестр подключений

Доступы к серверам, базам, контейнерам и FTP заводятся один раз и получают алиасы вида
`myproject/db`. Дальше ИИ-агент работает с алиасами: «выполни этот SQL на `myproject/db`»,
«положи файл на `myproject/files`». Пароли, ключи и строки подключения не покидают сервер —
агент получает транспорт и результат, а не креды. Работает как MCP-сервер и как команда `cr`
в терминале.

Реестр двухуровневый: отдельно **хосты** (адрес, пользователь, ключ или пароль, отпечаток
хост-ключа), отдельно **подключения**, которые на хост ссылаются. Один сервер — один набор
кредов, поверх него сколько угодно точек входа: шелл, файлы, пара контейнеров, база. У одного
проекта хостов может быть несколько: `shop/prod` и `shop/dev` — два сервера, один проект.

Запись агент делает с **разрешения человека**: один раз за сессию и один раз на проект, дальше
внутри проекта вопросов нет. Чтение не спрашивается никогда, а каждое действие целиком, вместе
с выводом, попадает в **журнал**. Рядом живут **заметки по проектам** — путь до кода на сервере,
версия PHP, имя контейнера с очередью, — чтобы агент не выяснял это заново каждую сессию.

## Установка из готового образа

Весь стенд — nginx и MCP-сервер — запечён в один образ. Разворачивание сводится к `docker pull`.
Если хотите дорабатывать сам стенд, ставьте [из исходников](#установка-из-исходников).

Нужен Docker, общая сеть и роутер — шаг [«Общая сеть и роутер»](#1-общая-сеть-и-роутер)
одинаков для обоих способов.

```sh
mkdir -p ~/registry && cd ~/registry
base=https://github.com/cat-of-summer/ConnectionRegistry---mcp-package/releases/latest/download
curl -fsSL -o docker-compose.yml "$base/docker-compose.yml"
curl -fsSL -o .env               "$base/default.env.example"
```

В `.env` задайте мастер-ключ — без него реестр поднимется «запертым»: метаданные и заметки
читаются, подключаться никуда нельзя.

```sh
echo "CR_MASTER_KEY=$(openssl rand -base64 32)" >> .env
docker compose up -d
```

Файлы берутся из релиза, а не из ветки: они генерируются при сборке и в git не лежат. Релиз
выпускается тем же тегом, что и образ, поэтому compose и образ всегда одной версии.

Готово, когда `docker compose ps` показывает `healthy`:

```sh
curl http://127.0.0.1:8090/health
docker compose exec registry cr doctor
```

Настройки — в `.env` рядом с `docker-compose.yml`:

| Параметр | Зачем менять |
|---|---|
| `CR_MASTER_KEY` | ключ шифрования секретов. Потеряли — секреты не восстановить |
| `EXTERNAL_ACCESS` | порт стенда на хосте, по умолчанию `8090` |
| `MCP_ACCESS` | порт MCP напрямую, мимо nginx |
| `HTTP_LOGIN`, `HTTP_PASSWORD` | пароль на страницы стенда; работает, когда заданы оба |
| `TRAEFIK_DOMAIN` | домен стенда, по умолчанию `registry.localhost` |
| `INSTANCE` | суффикс имён — чтобы поднять несколько стендов рядом |
| `BUNDLE_IMAGE` | другой тег образа вместо `:latest` |

Реестр, журнал, загрузки и артефакты лежат в томах `registry`, `logs`, `uploads`, `artifacts` —
они переживают `docker pull`.

> [!warning]
> Стенд слушает только `127.0.0.1` и должен там оставаться: в нём лежат ключи от боевых
> серверов. Если его всё же надо выставить наружу — за Traefik с HTTPS и с `HTTP_LOGIN`.

## Установка из исходников

Нужен Docker. Проверьте, что демон запущен:

```sh
docker info
```

### 0. Клонирование

Код сервера лежит в подмодуле `app/data`. Без него контейнер поднимется, но пять минут прождёт
`package.json` и уйдёт в ожидание — снаружи это выглядит как зависшая сборка.

```sh
git clone --recurse-submodules https://github.com/cat-of-summer/ConnectionRegistry---mcp-package.git
```

Если репозиторий уже склонирован без подмодулей:

```sh
git submodule update --init
```

### 1. Общая сеть и роутер

Стенд живёт в сети `network`. Если вы уже пользуетесь
[docker_toolkit](https://github.com/cat-of-summer/docker_toolkit), они подняты — пропустите шаг.

```sh
cd network  && cp .env.example .env && docker compose up -d
cd ../traefik && cp .env.example .env && docker compose up -d
```

### 2. Сам стенд

```sh
cd ../app && cp .env.example .env
# в .env задать CR_MASTER_KEY — cr key gen печатает подходящее значение
docker compose up -d --build
```

Первый запуск ставит зависимости; следите за `docker compose logs -f node`. Готово, когда в логе
появилось `команда cr готова` и `streamable http на 0.0.0.0:8932/mcp`.

### 3. Проверка

```sh
curl http://127.0.0.1:8090/health
docker compose exec node cr doctor
```

`cr doctor` называет всё, без чего стенд не работает: мастер-ключ, права на базу, каталоги.

## Подключение к ИИ-агенту

### Claude Code

```sh
claude mcp add --transport http registry http://127.0.0.1:8090/mcp
```

Проверьте, что подключилось: `claude mcp list` — в списке появится `registry`.

Дальше агенту достаточно сказать словами:

> Посмотри логи очереди на shop/prod и скажи, почему падают задания

Агент сам возьмёт нужный алиас, спросит разрешение на изменяющие действия и вернёт разбор.

### Другие клиенты

Стенд отдаёт стандартный MCP по двум транспортам.

**HTTP** (рекомендуется — SSH-соединения остаются тёплыми между вызовами):

```json
{
  "mcpServers": {
    "registry": { "type": "http", "url": "http://127.0.0.1:8090/mcp" }
  }
}
```

**stdio** (процесс на каждую сессию):

```json
{
  "mcpServers": {
    "registry": {
      "command": "docker",
      "args": ["compose", "-f", "/полный/путь/к/app/docker-compose.yml",
               "exec", "-T", "node", "npm", "run", "mcp:stdio"]
    }
  }
}
```

В stdio нет страницы подтверждений: если клиент не умеет спрашивать сам (elicitation), заявки
всё равно встают в очередь, но смотреть их придётся через `cr approve ls` в другом терминале.

### Подключиться к части инструментов

`/mcp` отдаёт весь набор. Хвост адреса сокращает его до названных групп: `/mcp/db+audit`,
`/mcp/shell`, `/mcp/core`. Стенд при этом один — просто у каждого подключения свой манифест.

Группы: `registry`, `notes`, `shell`, `files`, `docker`, `db`, `audit`. Складываются через `+`,
порядок не важен. Псевдонимы: `core` (registry, notes, shell, files), `ops` (registry, shell,
docker, audit), `minimal` (только registry). `registry_info` и `help` есть на любом адресе — иначе
агент, не нашедший инструмента, решил бы, что стенд неисправен.

Сессия MCP привязана к своему адресу: запрос с чужим `mcp-session-id` получит 400, а не молча
другой набор инструментов. В stdio адреса нет, и набор называют флагом:
`npm run mcp:stdio -- --tools=db+audit`.

## Первые хосты

Заводить доступы может и человек через `cr`, и агент через инструменты `host_set` / `conn_set`
/ `secret_set` — такая правка спрашивает человека каждый раз. Начать проще руками.

Секреты передаются **файлом или через stdin**, не аргументом: аргументы видны в `ps` и в
истории шелла. Из-под Windows это ещё и единственный надёжный путь — кириллица в аргументах
`docker exec` доезжает искажённой, файл в смонтированном каталоге доезжает как есть.

```sh
# хост: адрес, пользователь, пароль или ключ
docker compose exec node cr host add shop-prod --address 203.0.113.10 --user deploy --key-file /var/www/html/uploads/id_ed25519
docker compose exec -T node cr host add shop-dev --address 10.0.0.5 --user deploy --password - < dev.pw

# подключения поверх хоста: алиас всегда «проект/точка»
docker compose exec node cr conn add shop/prod       --kind shell  --host shop-prod --config '{"cwd":"/var/www/shop"}'
docker compose exec node cr conn add shop/dev        --kind shell  --host shop-dev
docker compose exec node cr conn add shop/files      --kind files  --host shop-prod --config '{"proto":"sftp","root":"/var/www/shop"}'
docker compose exec node cr conn add shop/queue      --kind docker --host shop-prod --config '{"container":"shop_queue","composeFile":"/opt/shop/docker-compose.yml"}'
docker compose exec -T node cr conn add shop/db      --kind db     --host shop-prod --password - < db.pw \
    --config '{"engine":"postgres","database":"shop","username":"shop"}'
```

`cr host add` с уже существующим алиасом правит его: поля, которых нет в команде, остаются
прежними — сменить порт можно, не повторяя пароль.

Первое подключение к хосту показывает отпечаток его ключа и просит подтвердить. Если отпечаток
известен заранее, его задают сразу: `--host-key SHA256:…`.

**База за SSH.** У `shop/db` есть хост, поэтому реестр ходит к базе через SSH-туннель:
`address` в настройках — это адрес базы *со стороны сервера*, по умолчанию `127.0.0.1`. Порт
базы наружу открывать не нужно. Подключение без хоста (`--host none`) идёт по сети напрямую —
так заводят базу, доступную извне.

**Docker.** Контейнеры удалённого сервера водятся его же `docker` по SSH: ни сокета наружу, ни
второго набора кредов. `container` в настройках — контейнер по умолчанию, чтобы агенту хватало
алиаса; `composeFile` и `workdir` делают `docker_compose` вызовом из нужного каталога.
Локального docker у реестра нет намеренно.

## Как это работает

### Подтверждения

Человека спрашивают редко и по делу: разрешение выдаётся не на действие, а на область работы.

**Чтение не спрашивается никогда** — список файлов, `SELECT`, логи контейнера, заметки, журнал.

**Запись** спрашивается дважды за сессию агента и дальше не спрашивается:

1. на первом изменяющем вызове — «разрешить этой сессии менять что-либо»;
2. на первой записи в каждый проект — «разрешить запись в проект shop».

После этого работа внутри разрешённого проекта идёт без вопросов: команды, файлы, `UPDATE`,
перезапуск контейнеров, заметки. Новый проект в той же сессии задаст только свой вопрос. Отказ
на втором вопросе оставляет проект **только на чтение** до конца сессии: повторно о нём не
спрашивают, сразу отвечают отказом. Отказ на первом запрещает запись во всех проектах сессии.

**Каждый раз** спрашиваются только доступы: `host_set`, `host_remove`, `secret_set`, `conn_set`,
`conn_remove`. Это не работа внутри проекта, а изменение того, куда и чем реестр вообще может
ходить, поэтому разрешение на проект их не покрывает.

Разрешения живут в памяти и умирают вместе с сессией MCP: новая сессия спрашивает заново. Что
уже выдано, показывает `registry_info`.

Сначала спрашивает сам клиент агента — штатным механизмом MCP elicitation. Если клиент этого не
умеет, заявка встаёт в очередь на `http://127.0.0.1:8090/approvals`, а вызов ждёт решения до
`CR_APPROVE_TIMEOUT` (по умолчанию 5 минут). Страница обновляется сама; с сервера то же
делается через `cr approve ls` и `cr approve yes <id>`. Не дождался — отказ, и это тоже
запись в журнале: агент видит, что ему отказали, а не что стенд сломался.

`db_query` разбирает SQL сам: `SELECT` выполняется сразу, `UPDATE` и `DROP` спрашивают. Несколько
запросов через `;` в одном вызове отклоняются — человек должен подтвердить ровно то, что уйдёт в
базу.

### Журнал

Записывается каждое действие: время, алиас, инструмент, аргументы, команда, код возврата,
решение по подтверждению, stdout и stderr **целиком**. Секреты маскируются — и по имени поля, и
по значению, если пароль ушёл в эхо команды.

Журнал лежит файлами JSONL в томе `logs`, без второй копии в базе. Крупный вывод уезжает в
отдельный файл рядом. Потолок — `CR_LOG_MAX_BYTES` (1 ГБ); при переполнении удаляются самые
старые файлы целиком.

Смотреть: страница `http://127.0.0.1:8090/audit`, `cr log tail`, `cr log show <id>`; агенту —
`audit_tail`, `audit_query`, `audit_show`.

### Файлы

Файлы ходят мимо MCP: гнать мегабайты через параметры инструмента означало бы платить за них
контекстом модели.

```sh
curl -F file=@dist/app.tar.gz http://127.0.0.1:8090/upload
```

В ответе `uri` вида `cr://uploads/…` — его передают в `files_put`. Маленький текстовый файл
можно положить и параметром `content`. С сервера: `files_read` возвращает текст (с потолком),
`files_get` кладёт файл в артефакты и возвращает ссылку. Дамп базы (`db_dump`) снимает штатный
`pg_dump` или `mysqldump` через тот же туннель и тоже отдаёт ссылку.

Путь без ведущего `/` считается от `root` подключения, абсолютный уходит как есть. Рекурсивного
удаления нет намеренно: снести дерево — это `ssh_exec`, где команда видна человеку целиком.

### Заметки

Два вида на проект: факты «ключ — значение» (`php.version = 8.3`, `deploy.path = /var/www/shop`)
и свободный текст («после деплоя дёрнуть очередь»). Ключ проекта — левая часть алиаса, поэтому
знание и доступ лежат под одним именем. Чтение свободно, запись входит в разрешение на проект.

```sh
docker compose exec node cr note set shop php.version 8.3
docker compose exec node cr note get shop
```

### Безопасность

- Ни один инструмент не возвращает пароль, ключ или строку подключения. `conn_info` отдаёт
  способ входа и отпечаток хоста, но не сам секрет.
- Секреты в реестре зашифрованы (AES-256-GCM, ключ выводится из `CR_MASTER_KEY`). Ключ лежит
  рядом с базой, поэтому шифрование защищает копию тома и бэкап, а не живой хост — от этого
  защищает то, что стенд слушает только `127.0.0.1`.
- Хост-ключ SSH проверяется строго. Ключ сервера, увиденного впервые, закрепляется молча:
  сверять его не с чем, а спрашивать человека не о чем. Дальше любое расхождение с закреплённым —
  отказ без вопросов. Так выглядит и подмена сервера, и честная переустановка; разобраться должен
  человек: `cr host pin <алиас> --fingerprint SHA256:…`. Отпечаток можно задать и заранее,
  при заведении хоста: `--host-key SHA256:…`.
- Смена мастер-ключа делает старые секреты нечитаемыми — `cr doctor` скажет об этом прямо.

## Что стенд умеет

Подробное описание каждого инструмента агент получает по протоколу и читает сам — дублировать
его здесь значит завести вторую копию, которая разъедется с первой на первой же правке. Ниже —
только карта.

| Группа | Инструменты |
|---|---|
| registry | `conn_list`, `conn_info`, `host_list`, `conn_check`; `host_set`, `conn_set`, `secret_set`, `host_remove`, `conn_remove` |
| notes | `notes_get`, `notes_search`; `notes_set`, `notes_remove` |
| shell | `ssh_exec`, `ssh_script` |
| files | `files_list`, `files_stat`, `files_read`, `files_get`, `files_uploads`; `files_put`, `files_move`, `files_remove`, `files_mkdir`, `files_chmod` |
| docker | `docker_ps`, `docker_logs`, `docker_inspect`; `docker_exec`, `docker_restart`, `docker_compose` |
| db | `db_tables`, `db_schema`, `db_query`, `db_dump` |
| audit | `audit_tail`, `audit_query`, `audit_show` |
| служебные | `registry_info` (состояние), `help` (разделы `aliases`, `approvals`, `files`, `db`, `docker`, `notes`, `audit`, `security`) |

После точки с запятой — то, что требует разрешения на запись.

Устройство стенда, которое агенту нужно знать, живёт в самом протоколе: **`instructions`**
показываются модели при подключении, **`help`** отдаёт подробности по требованию, ресурсы
`cr://connections`, `cr://audit/recent`, `cr://help/…` дают клиенту закрепить справку в контексте,
не тратя вызов.

Человеку — `docs/tools.md` (и `docs/tools.en.md`): справочник по всем инструментам с
параметрами. Он **генерируется** из самого сервера (`npm run docs` в `app/data`) и в git не
хранится. Генератор падает, если у какого-то инструмента пустое название или описание.

## Работа руками, без агента

```sh
docker compose exec node cr                 # справка по командам
docker compose exec node cr doctor          # состояние стенда
docker compose exec node cr conn ls         # что заведено
docker compose exec node cr log tail        # последние действия
docker compose exec node cr approve ls      # что ждёт разрешения
```

Из готового образа сервис называется `registry`: `docker compose exec registry cr ...`.

## Если что-то не работает

**`cr: not found`** — контейнер ещё ставит зависимости. Дождитесь в логе `команда cr готова`.

**Инструменты отвечают «реестр заперт»** — не задан или неверен `CR_MASTER_KEY`. `cr doctor`
различает «ключа нет» и «ключ не тот, которым заведён реестр».

**Вызов висит несколько минут и отказывает** — клиент не умеет спрашивать сам, а на
`/approvals` никто не нажал «Разрешить». Держите страницу открытой или отвечайте через
`cr approve`.

**«отпечаток хоста не совпал с закреплённым»** — ключ на сервере сменился или это не тот сервер.
Убедившись, что всё честно: `cr host pin <алиас> --fingerprint <новый>`.

**База отвечает «хост запрещает проброс портов»** — в `sshd_config` сервера стоит
`AllowTcpForwarding no`. Без проброса до базы за SSH не добраться: включите его или заведите
базу без хоста, если она доступна по сети.

**`pg_dump` жалуется на версию сервера** — в образе клиент PostgreSQL 17, он снимает дампы с
любого сервера не новее себя. Для более нового сервера поднимите `PG_CLIENT_VERSION` и
пересоберите.

**Пароль с кириллицей не подходит, хотя верный** — он передан аргументом из-под Windows и
доехал искажённым. Передавайте файлом: `--password-file`.

**502 от nginx после пересборки node** — nginx запомнил старый адрес контейнера.
`docker compose restart nginx`. В запечённом образе такого нет: там сервисы делят сетевое
пространство.

**Сессий SSH накопилось** — они закрываются по простою `CR_SSH_IDLE_MS`. Кто сейчас живой,
видно в `registry_info`.

## Обновления

При запуске стенд один раз спрашивает у GitHub, какой релиз последний, и сравнивает с собой.
Если версия новее — агент видит это в описании сервера сразу при подключении, а подробный
порядок действий лежит в `registry_info`, поле `обновление`.

Проверка ничего не блокирует. GitHub может лежать, ограничивать по частоте или быть недоступен
вовсе — на это отведено четыре секунды и перехват любых отказов, после чего стенд работает
дальше на текущей версии, а в ответе стоит «неизвестно», а не ошибка. Ответ GitHub — тег и дата
релиза — кэшируется на шесть часов в томе `registry`: неавторизованный лимит GitHub — 60 запросов
в час на адрес, а сервер перезапускается легко. Сравнение с собственным тегом при этом делается
заново при каждом чтении, поэтому после обновления стенд не продолжает предлагать версию, на
которую уже перешёл.

Версия у стенда одна — тег образа. Стенд читает её из хвоста `BUNDLE_IMAGE` в `.env`: это тот
самый ref, который правят при обновлении, и второй записи того же факта нет. В `registry_info` и
в `serverInfo` MCP она же стоит в поле версии; `unknown` означает, что стенд поднят без тега.

Обновление из релиза — это образ **и файлы релиза**, а не только образ: `docker-compose.yml`
описывает тома, порты и healthcheck, и между версиями они меняются. Новый образ со старым
compose поднимается неверно или не поднимается вовсе. Порядок:

```sh
V=1.1.0
R=https://github.com/cat-of-summer/ConnectionRegistry---mcp-package/releases/download/v$V

docker pull ghcr.io/cat-of-summer/connectionregistry---mcp-package:$V
curl -fsSLo docker-compose.yml "$R/docker-compose.yml"
curl -fsSLo .env.example       "$R/default.env.example"   # у GitHub имена с точки в начале запрещены
# сверить .env.example со своим .env: перенести появившиеся ключи, свои значения не терять
# в .env выставить BUNDLE_IMAGE=ghcr.io/cat-of-summer/connectionregistry---mcp-package:$V
docker compose up -d
```

Из исходников:

```sh
git pull && git submodule update --remote
dockerbundle generate
docker compose up -d --build
```

Единственный файл, который правится руками и не берётся из релиза, — `.env`, и главное в нём —
`CR_MASTER_KEY`: с другим ключом секреты в реестре не расшифруются. Сам реестр, журнал, загрузки
и артефакты лежат в томах и обновление переживают.

Тот же порядок агент получает из `registry_info` вместе с прямыми ссылками на файлы релиза — ему
не нужно уходить за документацией.

> [!warning]
> Проверка работает только на закреплённом теге. Если в `BUNDLE_IMAGE` стоит плавающий `latest`,
> сравнивать не с чем, и ответ честный: «неизвестно» плюс подсказка, что закрепить. Молчаливое
> «обновлений нет» здесь было бы хуже: оно звучало бы одинаково при любой выпущенной версии.

Выключается целиком: `CR_UPDATE_CHECK=0`. В закрытом контуре запрос всё равно упрётся в таймаут,
и четыре секунды на старте платятся впустую.

## Настройки

Всё в `app/.env`.

| Параметр | Зачем менять |
|---|---|
| `CR_MASTER_KEY`, `CR_MASTER_KEY_FILE` | мастер-ключ шифрования секретов — значением или файлом |
| `CR_LANG` | язык описаний инструментов: `ru`, `en`, `auto` |
| `CR_APPROVE_TIMEOUT` | сколько секунд ждать решения человека, по умолчанию 300 |
| `CR_LOG_MAX_BYTES` | потолок журнала, по умолчанию 1 ГБ |
| `CR_LOG_FILE_BYTES` | размер одного файла журнала, по умолчанию 64 МБ |
| `CR_LOG_INLINE_BYTES` | вывод крупнее этого уезжает в отдельный файл, по умолчанию 256 КБ |
| `CR_MAX_TEXT_BYTES` | потолок текста в одном ответе агенту, по умолчанию 128 КБ |
| `CR_DB_MAX_ROWS` | потолок строк в ответе `db_query`, по умолчанию 500 |
| `CR_MAX_OUTPUT_BYTES` | потолок вывода одной команды в памяти, по умолчанию 32 МБ |
| `CR_MAX_UPLOAD_BYTES` | потолок загрузки через `/upload`; выше 256 МБ — вместе с `CLIENT_MAX_BODY_SIZE` |
| `CR_SSH_IDLE_MS` | через сколько простоя закрывать SSH-соединение, по умолчанию 5 минут |
| `CR_EXEC_TIMEOUT` | таймаут одной команды, по умолчанию 2 минуты |
| `PUBLIC_BASE_URL` | база ссылок на страницы и артефакты в ответах агенту |
| `PG_CLIENT_VERSION` | версия `pg_dump` в образе, по умолчанию 17 |
| `CR_UPDATE_CHECK` | `0` выключает проверку обновлений — для контуров без выхода наружу |
| `CR_UPDATE_REPO`, `CR_UPDATE_IMAGE` | откуда брать обновления — для форков |

Версии образов зафиксированы намеренно — стенд должен давать одинаковый результат сегодня и
через полгода.

## Тесты

Тесты живут в подмодуле, рядом с кодом. Прогонять — в контейнере, там же, где живёт проект:

```sh
docker compose exec node npm test
```

По умолчанию прогон обходится без внешних серверов: классификатор SQL, маскирование, ротация
журнала, шифрование, схема разрешений, очередь подтверждений, бюджет манифеста и загружаемость
всех модулей инструментов.

Сквозной прогон против живых мишеней — `docker-compose.test.yml` в корне: два SSH-сервера и
две базы за ними, в сеть реестра не выставленные. Если `db_query` отвечает, значит он дошёл
через туннель, а не по прямой сети.

```sh
docker compose -f docker-compose.test.yml up -d
docker compose -f app/docker-compose.yml exec node env CR_E2E=1 npm test
docker compose -f docker-compose.test.yml down -v
```

Перед сквозным прогоном мишени заводятся в реестре один раз:

```sh
cd app
printf '%s' 'tester-пароль-стенда' > data/uploads/host.pw
printf '%s' 'shop-пароль-стенда'   > data/uploads/db.pw
docker compose exec node cr host add demo --address sshd_test --port 2222 --user tester --password-file uploads/host.pw
docker compose exec node cr conn add demo/shell  --kind shell  --host demo --config '{"cwd":"/config"}'
docker compose exec node cr conn add demo/files  --kind files  --host demo --config '{"proto":"sftp","root":"/config"}'
docker compose exec node cr conn add demo/docker --kind docker --host demo --config '{"container":"app"}'
docker compose exec node cr conn add demo/db     --kind db --host demo --password-file uploads/db.pw --config '{"engine":"postgres","address":"postgres_test","database":"shop","username":"shop"}'
docker compose exec node cr conn add demo/mysql  --kind db --host demo --password-file uploads/db.pw --config '{"engine":"mysql","address":"mysql_test","database":"shop","username":"shop"}'
rm data/uploads/host.pw data/uploads/db.pw
```

### Бюджет манифеста

`test/manifest.test.js` держит верхнюю границу на размер списка инструментов — того, что агент
вычитывает целиком при каждом подключении. Добавили инструмент или раздули описание — тест
упадёт и назовёт пять самых тяжёлых. Тот же тест ловит модуль, который не загружается, и
zod-схему, не сворачиваемую в JSON Schema.

## Из чего собран

Внутри: MCP-сервер на Node с SQLite, nginx как вход, клиенты `pg_dump` и `mysqldump`.

Репозитория два:

- **внешний**, этот — обвязка: docker-бандл, nginx, traefik, network, CI и README;
- **`app/data`** — подмодуль, ветка `app` этого же репозитория. Там сам сервер, CLI, тесты и
  генерируемый справочник.

Правка кода — это коммит в подмодуле плюс обновление указателя здесь.

Модули [docker_toolkit](https://github.com/cat-of-summer/docker_toolkit) — `nginx`, `node`,
`network`, `traefik` — подмодулями не являются: они запечены в проект и поднимаются как есть.
У `node` добавлен режим `NODE_MODE=mcp` и обёртки `bin`-команд в `PATH` — тем же способом, что
у модуля `playwright` того же тулкита.

### Как собирается образ

`nginx` и `node` сводит в один образ
[dockerbundle](https://github.com/cat-of-summer/DockerBundle---python): он читает те же
compose-файлы, что и стенд, и раскладывает сервисы по supervisord. Всё, что нужно знать
сборщику, — в `docker-bundle.yml`. Результат ложится в `dist/` и **в git не хранится**: CI
собирает его на каждом прогоне.

```sh
curl -fsSL https://raw.githubusercontent.com/cat-of-summer/DockerBundle---python/vX.Y.Z/install.sh | sh -s -- vX.Y.Z
dockerbundle generate
docker build -t registry dist/
```

Бинарь — ELF под Linux; на Windows запускать через WSL или в контейнере с `ubuntu:24.04`
(нужен glibc 2.38). Генератор подставляет значения из `app/.env`, если он есть, — поэтому
`dist/.env.example`, собранный на машине разработчика, содержит его мастер-ключ. В CI `.env` нет,
и релизный файл уходит с пустым ключом.

`traefik` и `network` в бандл не входят: они помечены `mode: off`. Без traefik стенд доступен по
опубликованному порту; маршрутизация по домену появляется, когда прокси поднят рядом.

Отличия запечённого стенда от сборки из исходников: код и зависимости ставятся на сборке образа,
а не при старте контейнера, и сервисы делят сетевое пространство, поэтому nginx ходит в реестр
по `127.0.0.1`.
